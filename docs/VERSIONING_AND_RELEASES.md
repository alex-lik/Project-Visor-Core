# Политика версионирования и релизов (Versioning & Release Policy)

В проекте **Project Visor** принята строгая политика управления жизненным циклом версий, основанная на стандарте **[Semantic Versioning 2.0.0 (SemVer)](https://semver.org/)** и отраслевых стандартах управления релизами.

---

## 1. Схема версионирования (SemVer 2.0.0)

Каждый релиз проекта идентифицируется версией формата:
$$\mathbf{v}\text{MAJOR}.\text{MINOR}.\text{PATCH}[-\text{PRERELEASE}]$$

Например: `v1.0.0`, `v1.1.0`, `v1.1.1`, `v2.0.0-rc.1`.

### 1.1. Правила инкремента версий

| Уровень | Когда инкрементируется | Примеры в Project Visor |
| :--- | :--- | :--- |
| **MAJOR** ($X.0.0$) | Несовместимые изменения API, кардинальное изменение схемы БД без автомиграции, удаление публичных MCP-инструментов, изменение формата аутентификации. | Удаление метода MCP, отказ от SQLite в пользу распределенного кластера с несовместимым форматом данных. |
| **MINOR** ($1.X.0$) | Новая функциональность с сохранением обратной совместимости. | Добавление ролей участников проекта (`editor`/`viewer`), поддержка новых провайдеров секретов, новые MCP-тулы, новые дашборды. |
| **PATCH** ($1.1.X$) | Исправление ошибок и уязвимостей, оптимизация производительности, рефакторинг без изменения API. | Исправление бага в проверке токена, фикс утечки памяти, оптимизация SQL-запроса, фикс верстки. |
| **PRERELEASE** (`-alpha.X`, `-beta.X`, `-rc.X`) | Предварительные сборки для нагрузочного и интеграционного тестирования перед релизом. | `v2.0.0-alpha.1` (ранний прототип), `v2.0.0-rc.1` (релиз-кандидат на стабилизации). |

## 2. Стратегия ветвления и релизных веток

Project Visor следует стратегии **Trunk-Based Development** с аннотированными релизными тегами и сервисными ветками поддержки:

```text
main  ──●───────●───────●───────●───────● (v1.2.0)
         \             /         \
feat/...  ●─────●─────●           \
                                   └── release/v1.1 ──● (v1.1.1 hotfix)
```

1. **`main` (Транк)**:
   - Всегда стабильная, компилируемая ветка, готовая к развертыванию в Production.
   - Прямой пуш запрещен; слияние только через Pull Request с успешным прохождением CI.
2. **Ветки фич и исправлений**:
   - `feat/<название>` — для нового функционала.
   - `fix/<название>` — для исправления ошибок.
   - `docs/<название>` — для документации.
3. **Релизные теги**:
   - Каждый релиз фиксируется аннотированным тегом Git: `git tag -a v1.1.0 -m "Release v1.1.0"`.
4. **Ветки поддержки (Release Branches)**:
   - При необходимости долгосрочной поддержки старых версий создается ветка `release/vX.Y`.

## 3. Политика тегирования Docker-образов

Для каждого релиза публикуются следующие теги контейнеров:

```text
projectvisor-visor:latest     -> Всегда указывает на последний стабильный релиз
projectvisor-visor:v1.1.0      -> Неизменяемый образ конкретной версии (Immutable Tag)
projectvisor-visor:v1.1        -> Плавающий тег минорной ветки (автообновление патчей)
projectvisor-visor:v1          -> Плавающий тег мажорной ветки
projectvisor-visor:sha-abc1234 -> Идентификатор конкретного git-коммита
```

> [!IMPORTANT]
> В production-окружениях рекомендуется использовать неизменяемый тег конкретной версии (например, `projectvisor-visor:v1.1.0`), чтобы исключить неконтролируемые сайд-эффекты при автоперезапусках контейнеров.

## 4. Политика устаревания (Deprecation Policy)

Мы придерживаемся принципа предсказуемости для интеграторов, фронтенда и AI-агентов, использующих MCP:

1. **Фаза объявления (Deprecation Notice)**:
   - Функционал или эндпоинт объявляется устаревшим в минорной версии ($MINOR$).
   - В документацию и код добавляется аннотация `@deprecated`.
   - В HTTP-ответах возвращаются заголовки:
     ```http
     Deprecation: true
     Sunset: Wed, 01 Jan 2027 00:00:00 GMT
     Link: </docs/migrations/v2>; rel="sunset"
     ```
2. **Фаза поддержки**:
   - Устаревший функционал гарантированно продолжает работать как минимум до следующего мажорного релиза ($MAJOR$).
3. **Фаза удаления (Removal)**:
   - Полное удаление функционала допускается **только** при переходе на новую мажорную версию.

## 5. Процедура экстренного выпуска патчей (Hotfix Workflow)

В случае обнаружения критической уязвимости или блокера в production:

1. От последнего релизного тега создается ветка `fix/cve-...` или `release/v1.1.x`.
2. Вносится минимально необходимое исправление.
3. Запускаются интеграционные тесты.
4. Выпускается инкремент патч-версии:
   ```bash
   npm run release -- patch
   ```
5. Исправление вливается в `main` (cherry-pick или merge).

---

## 6. Чек-лист подготовки планового релиза

Перед выпуском релиза:
- [ ] Все PR влиты в `main`.
- [ ] `npm run build` проходит без предупреждений и ошибок.
- [ ] Все юнит- и интеграционные тесты (`scripts/test-*.mjs`) завершаются со 100% успехом.
- [ ] Все изменения описаны в секции `[Unreleased]` файла `CHANGELOG.md`.
- [ ] Запуск скрипта релиза: `npm run release -- <minor|patch|major>`.
- [ ] Сборка и верификация Docker-образа с новым тегом: `docker compose build`.
- [ ] Публикация Release Notes и тега в Git.
